# 昇腾场景方案

面向客户方案沟通的静态 Demo。直接在浏览器中打开 `index.html` 即可查看。

场景选型按「业务负载 → 响应目标 → 配置参考」组织：

| 场景 | 业务量换算 | 选型重点 |
| --- | --- | --- |
| Coding | 开发者人数 × 每人每小时交互 ÷ 60 × 每次交互调用数 | 输入 / 输出 TPS；同时约束首字、输出节奏和平均交互耗时 |
| 聊天 / AI 客服 | 高峰每分钟新会话 × 每会话问答轮数 | 首字 TTFT p99、TPOT avg、达标参考问答 QPS |
| ChatBI | 每分钟问题 × 每问题模型调用数 | 首字 TTFT p99、平均问数完成预算；外部耗时单列 |

输入 / 输出 tokens 均指单次模型调用的平均负载，可在配置建议中修改。TPS = 模型调用 QPS × 对应 tokens；总吞吐 = 输入 TPS + 输出 TPS。多步任务按串行调用和相同平均负载粗估。聊天模型用于稳态高峰，不把会话到达量当作同时在线人数。

三个场景的步骤 1 均可选择推理模型，当前提供 DeepSeek V4 Flash 0731、GLM-5.3（Mock）和 GLM-5.3 Flash（待采集）。模型与卡型按场景分别保存；切换模型时保留人数、频率、输入输出及响应目标，并联动两处数据筛选。若当前卡型没有所选模型的记录，自动切换至该模型已有记录的卡型；无记录则保留卡型并显示待采集，不套用其他模型数据。

Coding 默认只需选择推理模型、开发者人数和使用档位，其余四项在「调整参数」中展开编辑。手动修改四项后显示「自定义」，收起保留修改；切换预设仅替换这四项，保留人数和响应目标。档位是演示假设，不是实测使用率，按所填人数参与所选强度估算：

| 使用档位 | 每人每小时交互 | 每次交互模型调用 | 单次输入 / 输出 tokens |
| --- | --- | --- | --- |
| 轻度 · 辅助编程 | 30 | 1 | 8192 / 1024 |
| 中度 · 持续协作（默认） | 60 | 2 | 8192 / 1024 |
| 重度 · Agent 密集使用 | 120 | 5 | 32768 / 2048 |

聊天机器人同样默认只展示模型、高峰每分钟新会话量和使用档位。每会话问答轮数、输入和输出长度在「调整参数」中展开；手动修改显示自定义，切换档位保留会话量、模型与响应目标。

| 聊天使用档位 | 每会话问答轮数 | 单轮输入 / 输出 tokens |
| --- | --- | --- |
| 轻度 · 简短问答 | 3 | 1536 / 256 |
| 中度 · 多轮客服（默认） | 6 | 3069 / 512 |
| 重度 · 知识库对话 | 10 | 8192 / 1024 |

以上为可调整的业务假设，不代表实测使用率。默认中度档保留原有负载；其他档位必须匹配所选模型和卡型的对应压测，不能套用中度档性能。

推荐配置先筛选响应约束，再选择单套调用吞吐最高的测试点；同时提供低延迟、高容量方案比较。容量同时受 QPS、输入吞吐、输出吞吐约束，避免原表 QPS 四舍五入造成少配。没有达标点时不生成达标推荐。各配置卡片直接展示估算套数、设备数量和总容量，未计冗余、流量不均、缓存收益、重试和跨套扩展损失。

数据依据：

- DeepSeek V4 Flash 0731 / Ascend 910B：实测参考，输入 3,069 / 输出 512 tokens，1P1D / 2 台。原始记录保存在 `DeepSeek_V4_Flash_0731_capacity_planning.html`，不作修改。
- GLM-5.3 / Ascend 910C：Mock 演示，输入 8,192 / 输出 1,024 tokens，1P1D / 2 台。仅用于 Coding 建模流程演示，不作为客户性能依据。Agent 密集使用预设没有对应负载压测，不输出设备建议。
- 其他模型 / 卡型组合：待采集。

首页实测数据区域和性能数据页均可按模型、卡型、输入长度、输出长度筛选。长度选项来自实际收录的数据组；输入改变时输出选项联动，仅展示真实存在的组合，不混合不同负载曲线。当前 DeepSeek / 910B 只有 3069 / 512，GLM / 910C 只有 8192 / 1024（Mock）；没有记录的组合显示待采集。长度筛选仅影响数据图表，不修改上方业务负载假设。

业务 tokens 与数据负载不匹配时，只更新需求，不外推新负载的 QPS、时延、设备数量或业务容量。匹配时给出的也只是参考估算，不构成业务 SLA 保证。ChatBI 的 SQL 执行等外部耗时为用户假设，首字仅代表首个模型调用；完整链路需单独压测。

步骤 2 同时提供响应目标与放大的场景体验区，步骤 3 比较配置。体验档位选择器位于左侧响应目标区，与配置卡片双向联动。选择负载匹配的档位，会按该参考点回填 TTFT p99（秒，向上保留两位小数）与 TPOT avg（毫秒，向上保留一位小数），可继续手动修改；交互完成预算保持不变。负载不匹配时仅切换回放，不回填目标。页面自动以推荐方案作为初始参考；无推荐时可选择已有参考点体验。Coding 展示 TypeScript 代码生成示例，聊天展示客服对话，ChatBI 展示 SQL 和分析步骤示例。仅保留步骤 2 的场景体验，导航为场景方案与性能数据，不再提供独立性能体验页。

体验窗口按参考点的平均 TTFT / TPOT 近似回放固定演示文本，不执行真实检索、数据库、Agent 工具或模型推理；输入问题不调用模型生成新的回答。SQL 标注未执行，不返回虚构的经营数据。

代码：`planning.js` 为可独立测试的业务计算，`planning-ui.js` 为场景表单和选型展示，`index.html` 包含页面样式、压测数据、图表与导航。

开发验证（Node.js，页面运行无需安装依赖）：

```sh
npm ci
npm test
```

测试覆盖业务量换算、负载边界、时延筛选、容量推算、无数据状态与页面交互。`happy-dom` 仅作为测试依赖，不参与页面运行。

三个场景的步骤 1 均展示当前输入 / 输出长度下的需求 QPS、输入 TPS、输出 TPS 和总吞吐。步骤 2 按所选参考点展示相同口径的单套聚合指标，以及单请求 Decode TPS（可优先使用记录中的 decode 字段，缺失时参考 1000 / TPOT(ms)）。TPS 即 tokens/s；Decode TPS 不能当作单套输出吞吐。QPS 与 TPS 需求是业务量换算值，不代表硬件实测能力。配置卡片中的总容量按单套 TPS × 套数估算。

业务负载与压测使用同一数据目录：优先按模型、卡型、输入长度、输出长度精确匹配；没有精确记录时只展示明确标注的其他负载参考，暂停业务配置数量推算。无数据时吞吐显示待测，不根据响应目标虚构 TPS。
